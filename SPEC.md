# Khoebo build spec

Prototype for the RSL Taxathon 2026, Challenge 1 (informal sector compliance).
Owner: Tumelo Mofubetsoana, New Empire AI. Live at https://khoebo-r8lc.vercel.app (the link to submit). Also served at khoebo.newempireai.online.
Submission due 6 November 2026. Spec written 28 October 2026.

## 1. What we are building and why

Judges score the entry on value, evidence, usability, fit for Lesotho, and whether the AI's decisions can be explained and checked. The prototype has to show three things:

1. A trader can log sales and file a return on a phone without help.
2. An officer can see who to follow up with, and why.
3. The three cases from the concept note: an ordinary trader, a seasonal trader whose nil returns are explained, and a case that goes to human review.

Anything that doesn't serve one of those is out of scope.

### In scope

- Landing page
- Trader chat, phone-sized, styled like a messaging app, powered by Claude with tool use
- Officer worklist and trader detail pages, built from the simulation output
- Demo tools: load a sample trader, simulate a reminder, reset

### Out of scope (goes in the pilot plan)

- Real WhatsApp or SMS
- Real voice transcription (voice notes are simulated)
- Accounts and logins
- Real payments
- Any connection to RSL systems (the Lekuka check on receipts is simulated, in `lib/lekuka.ts`)
- A database
- Sesotho UI text (structure strings so it can be added later)

## 6. The assistant

### How a request works

The server is stateless. The browser holds everything.

1. The browser sends `POST /api/chat` with `{ messages, state, action? }`:
   - `messages`: the last 20 chat turns (older turns are dropped; the state carries the records).
   - `state`: the full `TraderState` (below).
   - `action`: optional structured action from a button tap, such as `{ type: "confirm_return", period: "2026-Q3" }`. Button taps that change records always use `action`, never free text, so a trader can't confirm a return by accident.
2. The route validates the body with zod, rejects anything over 100 KB, and checks the message count against `MAX_MESSAGES_PER_SESSION`.
3. It runs the Claude tool loop (at most 5 tool rounds per request). Tool handlers in `lib/tools.ts` take the state, apply the change using `lib/ledger.ts` and `lib/tax.ts`, and return a result.
4. It responds with `{ reply, state, ui, tools, remaining }`. The browser saves the new state and renders the reply and UI blocks. `tools` lists the tools called, with their inputs, for the chat eval (added in step 4).

### Trader state

```ts
type TraderState = {
  version: 1;
  onboardingDone: boolean;
  profile: {
    name?: string;
    businessType?: string;
    district?: string;
    registered: "yes" | "no" | "not_sure" | null;
    language: "en";
  };
  entries: Entry[];
  returns: FiledReturn[];
  messageCount: number;
};

type Entry = {
  id: string;                    // short random id
  kind: "sale" | "purchase";
  amount: number;                // maloti, rounded to 2 decimals
  date: string;                  // YYYY-MM-DD
  note?: string;                 // e.g. "tomatoes"
  source: "text" | "voice" | "button" | "receipt";
  createdAt: string;             // ISO timestamp
  receipt?: {                    // only for entries saved from a receipt; the picture is never kept
    invoiceNumber?: string;
    deviceId?: string;
    lekuka: "verified" | "mismatch" | "not_found" | "no_code";
  };
};

type FiledReturn = {
  period: string;                // e.g. "2026-Q3"
  turnover: number;
  taxEstimate: number;
  confirmedAt: string;
  reference: string;             // "MOCK-" + random, clearly fake
  paid: boolean;
};
```

### Tools

All amounts in and out are maloti. Every handler is a pure function of `(state, input) → { state, result }` and has unit tests.

| Tool | Input | What the code does |
| --- | --- | --- |
| `save_profile` | `business_type?`, `district?`, `registered?`, `name?` | Updates the profile. Marks onboarding done when the first three are set. |
| `record_entry` | `kind`, and either `amount` or `quantity` + `unit_price`, plus `date?`, `note?` | Works out the amount (quantity × unit price is done here, never by the model). Rejects amounts of zero or less. Amounts over M20,000 come back as `needs_confirmation` so the assistant asks first. Date defaults to today, can't be in the future or more than 60 days back. Returns the entry plus the running totals for the Monday-to-Sunday week the entry falls in, with that week's dates (`week_of_entry`). |
| `correct_entry` | `entry_id` or `"last"`, `new_amount?`, `delete?` | Changes or removes one entry. Returns what changed. |
| `get_summary` | `period`: `this_week`, `last_week`, `this_month`, `filing_period` | Money in, money out, profit estimate (in minus out), number of entries, days with no entries. |
| `get_tax_estimate` | `period?` (default: current filing period) | Turnover, rate, estimate, due date, and `placeholder: true` while rates are unconfirmed. Adds `below_threshold: true` or `fixed_amount` when they apply. |
| `prepare_return` | `period` | Builds the pre-filled return and sends a `return_card` UI block with Confirm and Change buttons. Doesn't file anything. |
| `confirm_return` | `period`, `turnover` | Only callable when the request carries a matching `action` from the Confirm button. Saves a `FiledReturn` with a mock reference. |
| `start_payment` | `period` | Sends a `payment_card` UI block showing a mock mobile money payment. Marks the return paid only after the "Pay (demo)" button sends an action. |
| `start_registration` | none | Sends a `registration_card` listing what the trader will need and where to go. Use "RSL registration channel (to be confirmed)" rather than inventing a URL or office address. |
| `show_reminder` | none | Added in step 4. Sends a `reminder_card` for the current filing period, for the demo menu's "Simulate a reminder". |
| `offer_quick_replies` | `options` (1 to 6, each under 24 characters, or all ten districts) | Added in step 4. Sends a `quick_replies` UI block. The model has no other way to show quick replies. |

### UI blocks

The API can return these alongside the reply text:

- `quick_replies`: `{ options: string[] }`, at most 6, each under 24 characters (all ten districts for the district question)
- `entry_receipt`: the recorded entry, with a green tick and an "Undo" button
- `summary_card`: period label, money in, money out, profit, entries count
- `return_card`: period, turnover, estimated tax, due date, placeholder note, Confirm and Change buttons
- `payment_card`: amount, mock reference, "Pay (demo)" button, note that no real money moves
- `registration_card`: a checklist and the hand-off text
- `reminder_card`: due date, estimated tax, "File now" button
- `receipt_card`: what was read from a receipt (supplier, date, total), the simulated Lekuka result, and Save and Change buttons
- `placeholder_note`: the placeholder rate note, sent with `get_tax_estimate` and `confirm_return` so a tax amount in the reply text also shows the note (added in step 4)

### System prompt (write in `lib/prompt.ts`)

Claude Code writes the actual prompt. It must cover:

- **Who it is:** Khoebo, a prototype records and tax assistant for informal traders in Lesotho, built for the RSL Taxathon. It is not RSL staff and doesn't speak for RSL.
- **Tone:** friendly and plain, like a helpful neighbour who knows tax. At most three short sentences per message. One question at a time. No lectures, no threats, no mention of penalties unless the trader asks.
- **Numbers:** always call a tool to record or calculate. Never do arithmetic in the reply. Only quote numbers that a tool returned. Format money as "M1,840".
- **Understanding messages:** accept short and messy input ("350", "sold 350", "M3 50", "3 bags oranges 120 each"). Understand common Sesotho words: *ke rekisitse* (I sold), *ke rekile* (I bought), *kajeno* (today), *maobane* (yesterday), *chelete* (money). Reply only in English for now, with no Sesotho words or greetings added, until a Sesotho speaker has checked the replies.
- **When unsure:** if an amount or date is unclear, ask, offering quick replies where possible. Never guess an amount.
- **Off-topic:** politely say it only helps with business records and tax, then offer to get back to the task.
- **Tax law questions:** give only what the tools return. For anything beyond that, say it isn't sure and suggest the trader contact RSL. Never guess about the law.
- **Placeholder rates:** whenever it mentions tax owed, say it's an estimate.
- **Privacy:** if asked, explain that records stay on the trader's phone in this prototype and that RSL sees only a filed return.

### Safeguards

- Message cap per session from `MAX_MESSAGES_PER_SESSION` (default 60). The count lives in state, and the route also refuses requests whose `messages` array is over the limit.
- Max 500 characters per message, max 100 KB request body. A request with a receipt may be larger, up to about 2.9 MB, and the file must start the way its type says it should.
- Set a monthly spend limit in the Anthropic console before the link goes public.
- If the Vercel plan allows it, add a Firewall rate-limit rule on `/api/chat`.
- No message content in logs. Log only: request time, tool names called, token counts, errors.

```ts
  bands: [{ upTo: null, rate: 0.02, fixed: 0 }], // PLACEHOLDER: a flat 2% on all sales
  bandMethod: "whole",            // PLACEHOLDER: "whole" or "marginal"
  amountsPer: "year",             // PLACEHOLDER: threshold, band limits and fixed amounts are yearly
  filingPeriod: "quarterly",      // PLACEHOLDER
  dueDayAfterPeriodEnd: 20,       // PLACEHOLDER: due on the 20th of the following month
  reminderDaysBefore: 3,
  note: "This estimate uses a placeholder rate until RSL confirms the Simplified Business Tax rates.",
};
```

How the estimate for one filing period is worked out (`workOutTax` in `lib/tax.ts`):

1. Turnover is the sum of sales in the period.
2. If `amountsPer` is `"year"`, the threshold, band limits and fixed amounts are shared out evenly: a quarter of each for quarterly filing, a twelfth for monthly.
3. Turnover at or below the threshold pays nothing, and the result is marked `below_threshold`.
4. Bands run from the lowest turnover up. `upTo` is inclusive, and the last band has `upTo: null`.
   - `"whole"`: the band the turnover falls in sets the rate for all of it, plus that band's `fixed` amount. This suits a presumptive tax with a rate or fixed amount per turnover band.
   - `"marginal"`: each slice of turnover is taxed at its own band's rate, like income tax, plus the `fixed` amount of the band the turnover reaches. A first band with rate 0 gives "only the part above X is taxed".
5. The result is rounded to cents.

Whatever form the real rules take (a flat rate, a threshold, bands of rates, or fixed amounts per band), only this file changes. `checkTaxConfig` refuses broken settings (bands out of order, a rate outside 0 to 1, a missing last band) with a message naming the problem. `tax.test.ts` covers period boundaries, due dates, rounding, thresholds, both band methods and yearly amounts.

### Assistant and `/api/chat` (step 4)

- **Request shape.** Each message is `{ role, content, voice? }`. `voice: true` marks a voice note transcript; the model sees it prefixed with "[Voice note transcript]", and entries recorded from it get `source: "voice"`. Entries recorded after a button tap get `source: "button"`. User messages are capped at 500 characters, assistant messages at 4,000. Leading assistant messages are dropped, since the API needs the conversation to start with the trader.
- **Button actions** (`ChatActionSchema` in `lib/tools.ts`): `confirm_return { period, turnover }`, `change_return { period }`, `pay_return { period }`, `file_now { period }`, `undo_entry { entryId }`, `simulate_reminder`. An action is passed to the model as a "[Button tapped: ...]" user turn naming the tool to call.
- **`confirm_return`** only files when the request's action is `confirm_return` for the same period. It also checks that the turnover in both the action and the tool input still matches the records; if not, it fails with `records_changed` and the model shows the return card again. A period can't be filed twice.
- **`start_payment`** marks a return paid only when the request's action is `pay_return` for that period. Otherwise it shows the `payment_card`.
- **Periods.** Estimates and returns work for any period that has started, including the current one (so the demo can file the quarter in progress). Future periods are refused.
- **Tool results.** Every money value goes to the model as `{ amount, text }`, with `text` already formatted ("M1,840"), and dates as text ("20 January 2027"), so the model only copies. Handlers take a context with today's date, the time, and id and reference generators, so they stay pure and testable. Mock references look like `MOCK-7KQ2PX`.
- **Tool inputs** are zod schemas in `lib/tools.ts`, turned into the API's JSON schemas with `z.toJSONSchema`. They are kept loose; the ledger does the detailed checks and returns errors the model can explain. Unknown tools and bad input come back as `is_error` results and never change the state.
- **Model settings.** `ANTHROPIC_MODEL` (default `claude-haiku-5-5`), effort `medium`, `max_tokens` 4,096, adaptive thinking left at the model's default, no `temperature`. `tool_choice` is `auto`; after 5 tool rounds a final call uses `tool_choice: none` to get a reply. A refusal gets a fixed polite reply from `lib/strings.ts`.
- **System prompt.** `SYSTEM_PROMPT` in `lib/prompt.ts` is fixed and cached. `contextBlock()` is a second system block with today's date in Lesotho, the current filing period and a short profile: set-up status, profile fields, entry count, the last entry and filed returns.
- **Session cap.** `messageCount` goes up by one per request, including button taps. At the cap the route replies with the limit message without calling the model.
- **Errors.** 400 for bad JSON, a bad body or no trader message; 413 over 100 KB; 503 when rate limited; 502 for other API errors; 500 otherwise. The browser shows "Not sent. Tap to retry" for all of them. Logs hold the event, model, tool names, stop reason, token counts and time, never message text.

### Receipt upload and simulated Lekuka check (step 10b, 5 November 2026)

The owner asked for this after reading RSL's Lekuka public awareness session: informal traders buy from formal wholesalers, and many don't keep records of what they spend, so a receipt they already hold is an easy record. It's outside the original plan.

**How it works**

- A camera button in the composer opens a sheet: take a photo, choose a photo or PDF, or try one of three sample receipts.
- The photo is shrunk on the phone to at most 1568 px (`lib/receipts.ts`). PDFs are limited to 2 MB.
- The model reads it and calls `read_receipt` with what's printed. Code checks the amount and date, runs the simulated Lekuka check and shows `receipt_card`. **Nothing is saved until the trader taps Save**, which sends a structured action to `save_receipt`, the same pattern as filing a return. Change asks what's wrong, then uses `record_entry`.
- Saved as a purchase with `source: "receipt"`. It counts in money out and profit, and doesn't change the tax estimate, which is based on sales.

**Decisions**

- **Rule 1 holds.** Reading a printed total isn't calculating. The tool description and prompt say to copy it and never add up lines, and with no readable total there is no card. The thumb-over-total test confirms the model declines even when the lines above are clear.
- **Rule 3 holds.** The file is sent once, for that request. It isn't written to localStorage, not sent again with later messages, and not logged; server logs still hold only counts. The picture in the chat bubble is held in memory for that visit, and a reload removes it. A failed send after a reload asks the trader to choose the file again.
- **The picture does leave the phone.** It goes to Anthropic to be read, which the sheet says plainly before the trader picks a photo. For a pilot this belongs with the question of AI processing outside Lesotho (section 13).
- **The Lekuka check is simulated and labelled.** RSL says teams get no access to live systems, so `lib/lekuka.ts` holds seven made-up invoices. It never contacts RSL's real portal. A real connection needs an agreement with RSL and would be a pilot dependency.
- **The check takes only invoice details,** never who the trader is. This keeps the promise that records stay on the phone, and it must stay that way in a pilot.
- **A failed check is never an accusation.** It's usually a misread picture, so the wording stays neutral and the trader can still save.
- **Duplicates.** The same invoice number and device can only be saved once. Without an invoice number, the same date and total from another receipt shows a warning and the trader decides, because a second identical purchase is possible.
- **A large amount needs no second question,** since the trader sees it on the card before tapping Save.
- **Text on a receipt is data, never an instruction.** Tested with a receipt carrying instructions to the assistant.
- **Sample receipts** are drawn by `scripts/make_sample_receipts.py`, with made-up businesses all named "Sample ...", marked "SAMPLE - NOT A REAL INVOICE", with no RSL logo. The layout follows the receipt in RSL's session. The square code on them doesn't scan: Khoebo reads the printed code instead, so no QR library is needed and it also works on a photo of a printed code. Scanning real QR codes is a pilot option.

**Found by the eval and fixed:** on a creased receipt the model guessed a date hidden by a crease, wrong in 5 of 5 runs, while the total stayed right. The prompt now says to leave out any figure with a hidden or smudged digit. After the fix those runs show the card with "The date wasn't clear".
