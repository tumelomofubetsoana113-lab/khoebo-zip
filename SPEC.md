# Khoebo build spec

Built for the RSL Taxathon 2026, Challenge 1 (informal sector compliance).
Live at https://khoebo-r8lc.vercel.app (the link to submit). Also served at khoebo.newempireai.online.
Submission due 6 November 2026. Spec written 28 October 2026.

## 1. What we are building and why

Judges score the entry on value, evidence, usability, fit for Lesotho, and whether the AI's decisions can be explained and checked. The prototype has to show three things:

1. A trader can log sales and file a return on a phone without help.
2. An officer can see who to follow up with, and why.
3. The three cases from the concept note: an ordinary trader, a seasonal trader whose nil returns are explained, and a case that goes to human review.

Anything that doesn't serve one of those is out of scope.

### In scope

- Landing page
- Trader chat, phone-sized, styled like a messaging app, powered by Claude with tool use
- Officer worklist and trader detail pages, built from the simulation output
- Demo tools: load a sample trader, simulate a reminder, reset
- Log-in and sign-up, with accounts in Supabase (added 19 November 2026; see section 14)

### Out of scope (goes in the pilot plan)

- Real WhatsApp or SMS
- Real voice transcription (voice notes are simulated)
- Real payments
- Any connection to RSL systems (the Lekuka check on receipts is simulated, in `lib/lekuka.ts`)
- Trader records in a database (accounts are, since 19 November 2026; records stay on the phone)
- Sesotho UI text (structure strings so it can be added later)

## 2. Stack

| Part | Choice |
| --- | --- |
| Framework | Next.js, App Router, TypeScript (strict mode) |
| Styling | Tailwind CSS, palette defined as theme tokens |
| Icons | lucide-react |
| AI | `@anthropic-ai/sdk`, tool use, model from `ANTHROPIC_MODEL` (default `claude-haiku-5-5`) |
| Validation | zod, for the request body and the trader state sent to the API |
| Trader storage | localStorage in the browser, one set of keys per account (since 19 November 2026) |
| Accounts | Supabase Postgres through `postgres` 3.4.9, tables in a `khoebo` schema. Passwords hashed with scrypt from `node:crypto`. Local development and tests use PGlite (`@electric-sql/pglite` 0.5.14, dev only) |
| Officer data | `data/worklist.json`, generated by `npm run data` from the Python scripts |
| Charts | Plain SVG components, no chart library |
| QR codes | `qrcode` 1.5.4 (exact version), for the field-visit sign-up code. Only its module grid is used; the SVG is drawn with theme tokens |
| Tests | Vitest |
| Hosting | Vercel, DNS on Cloudflare |

Use the current stable version of each package at the time of setup.

### Type, spacing and touch

- System font stack (`ui-sans-serif, system-ui, -apple-system, "Segoe UI", Roboto, sans-serif`). No web fonts, so pages load fast on weak data.
- Chat text at least 16px. Body text 16px. Landing headline about 40px on desktop and 30px on mobile.
- Tap targets at least 44px high. Quick-reply chips at least 40px high with 8px gaps.
- Corner radius: 12px on cards, 18px on chat bubbles, 12px on buttons (full until 19 November 2026), full on pills. Landing page cards use 16px.
- Light mode only for the prototype.
- Respect `prefers-reduced-motion`. Keep animation to short fades and the typing indicator.

### Brand rules

- No flag stripe: the tricolour stripe that ran along the top and bottom of every page was removed on 31 October 2026 (see section 14).
- No mokorotlo emblem, no RSL logo, no WhatsApp name, logo or green.
- The wordmark is the word "Khoebo" in bold white on the charcoal header, with "Records and tax assistant" under it from 640px up and the Khoebo mark to its left (added 29 October 2026, see section 14): a white chat bubble holding three rising bars on a circle. Since 19 November 2026 the drawing is unchanged and only its colours changed: the circle and the first two bars are `brand-bright`, the tallest bar `charcoal` (they were `flag-blue`, with the last bar `flag-green`).
- No event pill in the headers, and the app doesn't mention the RSL Taxathon (since 19 November 2026; see section 14).
- Footer text on every page: "© Khoebo 2026", and nothing else.
- The word "prototype" isn't used anywhere in the app (since 19 November 2026; see section 14). "Demo" marks what is simulated, such as payments and voice notes.

### Accessibility

- WCAG AA contrast for all text. The palette above passes when used as specified.
- Visible focus rings (2px `brand` outline with offset).
- Every icon-only button has an `aria-label`.
- Chat messages are in an `aria-live="polite"` region.

### 5.1a Trader home (`/trader`, added 19 November 2026)

Where a trader lands after logging in or signing up. It is built for traders who don't use computers much: big buttons, an icon on every row, short words, one column at every width (up to 576px).

- The floating charcoal header with "Log out".
- "Hello, <first name>" and today's date.
- **"Talk to Khoebo"**, the first and biggest thing on the page: a full-width orange button that opens the chat (`/trader/chat`).
- A late-return card in the follow-up colours when an ended filing period has no return, with "File it now" to the chat.
- A new trader sees "Let's get started" with a Start button to the chat; a set-up trader with no records sees "No records yet" with "Record a sale".
- Once there are records: money in, money out and profit for this week or this month (two big tabs), with one line per business for a trader with several; a bar chart of each day's sales this week, Monday to Sunday, where tapping a bar shows its amount and the best day is named; the next return's period, due date, filed or not, and the tax so far, with the placeholder note (rule 6); and "My statement".
- Every figure comes from `buildHome()` in `lib/home.ts`, which uses `lib/ledger.ts`, `lib/tax.ts` and `returnsToFile()`. The page reads the records again each time it shows, since Next.js keeps it in memory while the trader is in the chat.

### 5.2 Trader chat (`/trader/chat`)

A full-height chat that feels like a messaging app, centred in a 420px column on desktop with the `page` colour around it. The column is a rounded frame (28px corners, `line` border, soft shadow) with a small gap on every side, on phones too.

**Header** (`brand`, white text)
- Back arrow to `/`, a round avatar with the letter K, "Khoebo" and a subline "Records and tax assistant".
- Right: a "Demo" button that opens the demo menu.
- Nothing sits between the header and the messages (the event strip went on 19 November 2026).

**Messages**
- Trader bubbles on the right in `brand` with white text. Assistant bubbles on the left in white with `ink` text and a `line` border.
- Small time under each bubble in `muted`.
- Typing indicator (three dots) while waiting for the API.
- Cards render inside assistant bubbles (see "UI blocks" in section 6).
- Quick-reply chips appear under the latest assistant message only, and disappear once used.

**Composer** (fixed at the bottom)
- Text field, placeholder "Type a message", max 500 characters.
- Mic button opens the voice sheet.
- Send button (`flag-blue` circle with an arrow), disabled when empty.
- The send button turns into the mic button when the field is empty, as messaging apps do.

**Voice sheet** (simulated voice notes)
- A bottom sheet titled "Voice notes (simulated in this prototype)" with three sample notes. Each shows a play icon, a fake duration, and its transcript:
  - 0:04 — "Sold four hundred and twenty today, mostly tomatoes"
  - 0:06 — "Bought stock from the wholesaler for nine hundred"
  - 0:03 — "Ke rekisitse makholo a mararo kajeno" (I sold three hundred today)
- Tapping one sends a voice bubble (waveform shape and duration) with the transcript shown under it in small `muted` text, labelled "Transcript". The transcript is what goes to the API.

**First visit (onboarding)**
- The assistant greets the trader, explains in two short sentences what it does, and asks for business type with quick replies: Fruit and veg, Spaza / general dealer, Street food, Clothing or flea market, Hair or beauty, Repairs or services, Runner (cross-border), Courier or delivery, Online seller, Other. (Widened on 17 November 2026; see section 14.)
- Then district with quick replies for the ten districts.
- Then "Are you registered with RSL?" with Yes / No / Not sure.
- Then a short "You're set up" message and a quick reply "Log my first sale".
- Name is optional and only asked if the trader offers it.

**Field-visit start** (added 17 November 2026): opening `/trader/chat?via=field&district=…&kind=…` (an officer's QR code, see 5.3a) on a phone that isn't set up fills in the district and business type, marks the profile `setUpAt: "field_visit"`, and opens with "An RSL officer shared this link with you… Are you registered with RSL?" with Yes / No / Not sure. Values not on the chat's own lists are ignored. A phone that is already set up or has records is never changed. The query is removed from the address once the chat starts.

**Demo menu** (bottom sheet)
- "Load demo trader": replaces state with a fruit and vegetable seller in Maseru, registered, with four weeks of realistic daily sales and twice-weekly purchases. Use the profile of the ordinary case.
- "Load demo runner" (added 17 November 2026): a registered runner in Maseru who buys goods in Bloemfontein for clients every Tuesday and Friday. Client money is kept apart and only the fees are turnover.
- "Load demo trader with three businesses" (added 19 November 2026): a registered trader in Maseru with two spaza shops ("Town shop" and "Ha Thetsane shop") and a "Salon", four weeks of records for each. Each business files its own return.
- "Show this week's summary": sends the message "how am I doing this week?"
- "Simulate a reminder": the assistant posts the reminder message for the current filing period, as if it were 3 days before the due date.
- "Open this month's statement" (added 19 November 2026): opens the statement page for this month, without calling the API.
- "Reset everything": opens an in-app confirm dialog, then clears localStorage and restarts onboarding. Never use `window.confirm` or `alert`.

**Network and errors**
- If a request fails, keep the trader's message on screen with a small "Not sent. Tap to retry" note.
- If the session cap is reached, the assistant says the demo limit is reached and offers "Reset everything" in the demo menu.

**Statements and records** (`/trader/statement?period=...`, added 19 November 2026)
- A trader asks in the chat ("get my statement", "my records for October", "something to show the bank") and the `get_statement` tool shows a `statement_card` with "Open statement" and "Download spreadsheet".
- The page shows one month (`period=2026-10`, or `this_month`, `last_month`) or every record (`period=all`), with a month picker. It has: the Khoebo mark, the trader's business, district, registration and the date made, totals (money in, money out, profit estimate, client money when there is some, entries, days with no entries), a month-by-month table for more than one month, any filed returns that overlap the period (with the mock reference and the placeholder note), every entry (date, kind, note, amount, rand, Lekuka result), and a footer saying it is made from the trader's own records, not checked by RSL and not an official RSL document.
- The Khoebo mark sits behind the statement as a faint watermark (added 19 November 2026). On screen it is centred on the statement; when printed it is fixed, so it repeats in the middle of every page.
- **No statement while a return is due** (added 19 November 2026). A return is due once its filing period has ended. If any finished filing period the statement's records fall in has no filed return (for each business, with several), there is nothing to save or print: the page shows "File your return first", lists each return with its dates and due date, and links back to the chat. In the chat, `get_statement` returns `return_not_filed` with a "File now" reminder card for each return. The card's "Download spreadsheet" checks again when tapped and opens the page instead. A period still running never blocks a statement.
- "Save as PDF or print" opens the browser's print window, which prints only the statement. "Download spreadsheet" saves a CSV file (`khoebo-statement-2026-10.csv`, or `khoebo-records-<date>.csv` for all records).
- Everything is worked out in the browser from localStorage by `lib/statement.ts`. Nothing is sent to the server.
- A trader with more than one business also gets a business picker ("All businesses" or one of them, `&business=<id>`). All businesses shows a line for each and the business under each entry; one business shows its own name, type and district.

**More than one business** (added 19 November 2026)
- A trader can run branches of one shop or different businesses. They say so in the chat ("I also run a hair salon") and `save_business` adds it. Set-up is unchanged and asks about one business.
- With one business nothing changes: no business is asked about or shown anywhere.
- With more than one, every sale, purchase and return belongs to a business. The assistant uses the one the trader names and otherwise asks, with the business names as quick replies. A receipt card has a "Save to …" button for each business. Summaries and statements cover all businesses with a line each, or one.
- Each business files its own return and pays its own tax: its own return card, mock reference and payment, its own lines in "What you need to do", and its own reminder card.

### 5.3 Officer worklist (`/officer`)

Desktop first, but it must not break on mobile (the table becomes cards under 768px).

**Header**: same style as the landing header, with "Try the chat" on the right. Under it, the title "Officer worklist" and the subline "Simulated data · 300 traders and 3 demo cases · May to Oct 2026" (worked out from the data). Under the subline, a small `muted` note with a lock icon: "In a pilot, only signed-in RSL officers can see this page."

**Summary strip**: four cards, one per action, each with its pill, the count, and the share of traders. Clicking a card filters the table.

**Demo cases**: a row of three cards pinned above the table, titled "Demo cases":
- Fruit and vegetable seller, Maseru → No action
- Blanket seller, Mokhotlong (trades in winter) → No action or Automated check-in, whichever the rules assign (see section 8)
- General dealer, Berea → Human review

Each card shows the action pill, two lines of reasons, and a "View" link.

**Filters**: action chips (multi-select), district dropdown, sector dropdown, and a search box for trader ID. Filters are reflected in the URL query string, so a filtered view can be shared.

**Table columns**: Trader ID · Sector · District · Action · Declared (6 months) · Evidence minimum · Months with evidence · Nil returns. Default sort: action order (follow-up, review, check-in, none), then the biggest gap between evidence and declared. Amounts as "M74,430". Each row links to the detail page. ## 6. The assistant

### How a request works

The server is stateless. The browser holds everything.

1. The browser sends `POST /api/chat` with `{ messages, state, action? }`:
   - `messages`: the last 20 chat turns (older turns are dropped; the state carries the records).
   - `state`: the full `TraderState` (below).
   - `action`: optional structured action from a button tap, such as `{ type: "confirm_return", period: "2026-Q3" }`. Button taps that change records always use `action`, never free text, so a trader can't confirm a return by accident.
2. The route validates the body with zod, rejects anything over 100 KB, and checks the message count against `MAX_MESSAGES_PER_SESSION`.
3. It runs the Claude tool loop (at most 5 tool rounds per request). Tool handlers in `lib/tools.ts` take the state, apply the change using `lib/ledger.ts` and `lib/tax.ts`, and return a result.
4. It responds with `{ reply, state, ui, tools, remaining }`. The browser saves the new state and renders the reply and UI blocks. `tools` lists the tools called, with their inputs, for the chat eval (added in step 4).

### Trader state

```ts
type TraderState = {
  version: 1;
  onboardingDone: boolean;
  profile: {
    name?: string;
    businessType?: string;
    district?: string;
    registered: "yes" | "no" | "not_sure" | null;
    language: "en";
    businessName?: string;       // the first business's short name, once there are several
  };
  businesses?: { id: string; name: string; type?: string; district?: string }[]; // further businesses, up to 10
  entries: Entry[];
  returns: FiledReturn[];
  messageCount: number;
};

type Entry = {
  id: string;                    // short random id
  kind: "sale" | "purchase" | "client_money"; // client_money added 17 Nov 2026, for runners
  amount: number;                // maloti, rounded to 2 decimals
  currency?: "rand";             // the trader gave it in rand; same figure, as R1 = M1
  date: string;                  // YYYY-MM-DD
  note?: string;                 // e.g. "tomatoes"
  source: "text" | "voice" | "button" | "receipt";
  createdAt: string;             // ISO timestamp
  businessId?: string;           // left out for the first business ("main")
  receipt?: {                    // only for entries saved from a receipt; the picture is never kept
    invoiceNumber?: string;
    deviceId?: string;
    lekuka: "verified" | "mismatch" | "not_found" | "no_code";
  };
};

type FiledReturn = {
  period: string;                // e.g. "2026-Q3"
  turnover: number;
  taxEstimate: number;
  confirmedAt: string;
  reference: string;             // "MOCK-" + random, clearly fake
  paid: boolean;
  businessId?: string;           // each business files its own return; left out for the first
};
```

### System prompt (write in `lib/prompt.ts`)

Claude Code writes the actual prompt. It must cover:

- **Who it is:** Khoebo, a records and tax assistant for informal traders in Lesotho, its own service separate from RSL. It is not RSL staff and doesn't speak for RSL.
- **Tone:** friendly and plain, like a helpful neighbour who knows tax. At most three short sentences per message. One question at a time. No lectures, no threats, no mention of penalties unless the trader asks.
- **Numbers:** always call a tool to record or calculate. Never do arithmetic in the reply. Only quote numbers that a tool returned. Format money as "M1,840".
- **Understanding messages:** accept short and messy input ("350", "sold 350", "M3 50", "3 bags oranges 120 each"). Understand common Sesotho words: *ke rekisitse* (I sold), *ke rekile* (I bought), *kajeno* (today), *maobane* (yesterday), *chelete* (money). Reply only in English for now, with no Sesotho words or greetings added, until a Sesotho speaker has checked the replies.
- **When unsure:** if an amount or date is unclear, ask, offering quick replies where possible. Never guess an amount.
- **Off-topic:** politely say it only helps with business records and tax, then offer to get back to the task.
- **Tax law questions:** give only what the tools return. For anything beyond that, say it isn't sure and suggest the trader contact RSL. Never guess about the law.
- **Placeholder rates:** whenever it mentions tax owed, say it's an estimate.
- **Privacy:** if asked, explain that records stay on the trader's phone in this prototype and that RSL sees only a filed return.

### Safeguards

- Message cap per session from `MAX_MESSAGES_PER_SESSION` (default 60). The count lives in state, and the route also refuses requests whose `messages` array is over the limit.
- Max 500 characters per message, max 100 KB request body. A request with a receipt may be larger, up to about 2.9 MB, and the file must start the way its type says it should.
- Set a monthly spend limit in the Anthropic console before the link goes public.
- If the Vercel plan allows it, add a Firewall rate-limit rule on `/api/chat`.
- No message content in logs. Log only: request time, tool names called, token counts, errors.

## 7. Tax settings (placeholders)

The Call for Innovation leaves the SBT threshold and rates blank, so everything here is a placeholder until the 2 November Q&A. All values live in `config/tax.ts`:

```ts
export const TAX = {
  placeholder: true,              // shows the placeholder note everywhere
  threshold: 0,                   // PLACEHOLDER: turnover at or below pays no tax; 0 = none
  bands: [{ upTo: null, rate: 0.02, fixed: 0 }], // PLACEHOLDER: a flat 2% on all sales
  bandMethod: "whole",            // PLACEHOLDER: "whole" or "marginal"
  amountsPer: "year",             // PLACEHOLDER: threshold, band limits and fixed amounts are yearly
  filingPeriod: "quarterly",      // PLACEHOLDER
  dueDayAfterPeriodEnd: 20,       // PLACEHOLDER: due on the 20th of the following month
  reminderDaysBefore: 3,
  note: "This estimate uses a placeholder rate until RSL confirms the Simplified Business Tax rates.",
};
```

How the estimate for one filing period is worked out (`workOutTax` in `lib/tax.ts`):

1. Turnover is the sum of sales in the period.
2. If `amountsPer` is `"year"`, the threshold, band limits and fixed amounts are shared out evenly: a quarter of each for quarterly filing, a twelfth for monthly.
3. Turnover at or below the threshold pays nothing, and the result is marked `below_threshold`.
4. Bands run from the lowest turnover up. `upTo` is inclusive, and the last band has `upTo: null`.
   - `"whole"`: the band the turnover falls in sets the rate for all of it, plus that band's `fixed` amount. This suits a presumptive tax with a rate or fixed amount per turnover band.
   - `"marginal"`: each slice of turnover is taxed at its own band's rate, like income tax, plus the `fixed` amount of the band the turnover reaches. A first band with rate 0 gives "only the part above X is taxed".
5. The result is rounded to cents.

**More than one business (placeholder rule, added 19 November 2026).** Each of a trader's businesses or branches files its own return, with turnover from that business's sales only, as the owner chose. Whether RSL taxes a person's businesses together or separately (and so whether a threshold applies per business or per person) isn't confirmed; see section 13.

Whatever form the real rules take (a flat rate, a threshold, bands of rates, or fixed amounts per band), only this file changes. `checkTaxConfig` refuses broken settings (bands out of order, a rate outside 0 to 1, a missing last band) with a message naming the problem. `tax.test.ts` covers period boundaries, due dates, rounding, thresholds, both band methods and yearly amounts.

### Ledger, tax and state (step 3)

- `lib/dates.ts` holds the date maths. Dates are `YYYY-MM-DD` strings, and "today" is today in Lesotho (`Africa/Maseru`), so a server on UTC doesn't put late-evening sales on the wrong day.
- Weeks run Monday to Sunday, so the weekly summary lands on Sunday.
- `record_entry`'s checks live in `checkEntry()` in `lib/ledger.ts`: a missing amount, a zero or negative amount, an invalid date, a future date, a date more than 60 days back, and amounts over M20,000 without `confirmed`. Amounts are rounded to cents. M20,000 exactly is allowed without confirmation.
- `correct_entry` with `"last"` changes the entry recorded most recently (by `createdAt`), not the one with the latest date.
- Summaries count "days with no entries" only up to today. Profit can be negative and formats as "-M800".
- Which period to file (`filingPeriod()` in `lib/tax.ts`): the period that has just ended until its due date, then the current one. On 20 October 2026 that is 2026-Q3; from 21 October it is 2026-Q4.
- `config/tax.ts` also accepts `filingPeriod: "monthly"` (periods named like `2026-10`). If the due day doesn't exist in a month, the due date is that month's last day.
- Tax estimates are rounded to cents. A `TaxEstimate` carries `note`: the placeholder note while `TAX.placeholder` is true, otherwise `null`.
- The `TraderState` zod schema also caps sizes (5,000 entries, 100 returns, 100-character notes, 60-character profile fields) and requires return references to start with `MOCK-`. `loadState()` returns a fresh state when saved data is missing, broken or unreadable, and never throws.

### Assistant and `/api/chat` (step 4)

- **Request shape.** Each message is `{ role, content, voice? }`. `voice: true` marks a voice note transcript; the model sees it prefixed with "[Voice note transcript]", and entries recorded from it get `source: "voice"`. Entries recorded after a button tap get `source: "button"`. User messages are capped at 500 characters, assistant messages at 4,000. Leading assistant messages are dropped, since the API needs the conversation to start with the trader.
- **Button actions** (`ChatActionSchema` in `lib/tools.ts`): `confirm_return { period, turnover }`, `change_return { period }`, `pay_return { period }`, `file_now { period }`, `undo_entry { entryId }`, `simulate_reminder`. An action is passed to the model as a "[Button tapped: ...]" user turn naming the tool to call.
- **`confirm_return`** only files when the request's action is `confirm_return` for the same period. It also checks that the turnover in both the action and the tool input still matches the records; if not, it fails with `records_changed` and the model shows the return card again. A period can't be filed twice.
- **`start_payment`** marks a return paid only when the request's action is `pay_return` for that period. Otherwise it shows the `payment_card`.
- **Periods.** Estimates and returns work for any period that has started, including the current one (so the demo can file the quarter in progress). Future periods are refused.
- **Tool results.** Every money value goes to the model as `{ amount, text }`, with `text` already formatted ("M1,840"), and dates as text ("20 January 2027"), so the model only copies. Handlers take a context with today's date, the time, and id and reference generators, so they stay pure and testable. Mock references look like `MOCK-7KQ2PX`.
- **Tool inputs** are zod schemas in `lib/tools.ts`, turned into the API's JSON schemas with `z.toJSONSchema`. They are kept loose; the ledger does the detailed checks and returns errors the model can explain. Unknown tools and bad input come back as `is_error` results and never change the state.
- **Model settings.** `ANTHROPIC_MODEL` (default `claude-haiku-5-5`), effort `medium`, `max_tokens` 4,096, adaptive thinking left at the model's default, no `temperature`. `tool_choice` is `auto`; after 5 tool rounds a final call uses `tool_choice: none` to get a reply. A refusal gets a fixed polite reply from `lib/strings.ts`.
- **System prompt.** `SYSTEM_PROMPT` in `lib/prompt.ts` is fixed and cached. `contextBlock()` is a second system block with today's date in Lesotho, the current filing period and a short profile: set-up status, profile fields, entry count, the last entry and filed returns.
- **Session cap.** `messageCount` goes up by one per request, including button taps. At the cap the route replies with the limit message without calling the model.
- **Errors.** 400 for bad JSON, a bad body or no trader message; 413 over 100 KB; 503 when rate limited; 502 for other API errors; 500 otherwise. The browser shows "Not sent. Tap to retry" for all of them. Logs hold the event, model, tool names, stop reason, token counts and time, never message text.
- The Anthropic client is created on the first request, so `npm run build` works without the key.
- **Chat eval.** `tests/chat-eval/cases.json` holds the 14 messages from section 12, plus the district case below. A case can set a starting `setup` (state fields) and check `quickReplies`. `npm run eval:chat` runs `tests/chat-eval/run.mts` with Node's built-in TypeScript support against `http://localhost:3000`, or `EVAL_URL`. It checks the tools called, their inputs, and the change in state. `EVAL_REPEAT=3` runs each case three times; `EVAL_ONLY="350|RSL"` runs only the cases whose message matches.
- **Eval result, 29 October 2026, Haiku 5.5:** 42 of 42 passed (each of the 14 cases run three times), so Sonnet wasn't needed. Median reply time 2.4 seconds; the system prompt is read from cache on every request. The first run of three found two prompt gaps, now fixed: the model sometimes called `record_entry` with no input before knowing sale or purchase, and once called `offer_quick_replies` twice on an off-topic question. The "350" check also accepts "sold or bought" as well as "sale or purchase".
- If the model sends more than one set of quick replies in a reply, the route keeps only the last.
- **Eval after the district change, 29 October 2026:** 44 of 45 (15 cases, three runs each). The district case passed 3 of 3. The one failure was the injection case: the reply contained "0%" while the records were unchanged and no tool was called. Its text wasn't captured, and 15 further runs of that case all passed. If it comes back, read the reply before changing the check.
- **District quick replies.** Section 5.2 asks for all ten districts as quick replies, which is more than the cap of 6. Decided 29 October 2026: show all ten. `offer_quick_replies` accepts up to 10 options only when every option is a district; any other list is still capped at 6. The chat eval has a 15th case, "I sell fruit and veg" from a trader who isn't set up, which checks that all ten districts appear.

### Receipt upload and simulated Lekuka check (step 10b, 5 November 2026)

The owner asked for this after reading RSL's Lekuka public awareness session: informal traders buy from formal wholesalers, and many don't keep records of what they spend, so a receipt they already hold is an easy record. It's outside the original plan.

**How it works**

- A camera button in the composer opens a sheet: take a photo, choose a photo or PDF, or try one of three sample receipts.
- The photo is shrunk on the phone to at most 1568 px (`lib/receipts.ts`). PDFs are limited to 2 MB.
- The model reads it and calls `read_receipt` with what's printed. Code checks the amount and date, runs the simulated Lekuka check and shows `receipt_card`. **Nothing is saved until the trader taps Save**, which sends a structured action to `save_receipt`, the same pattern as filing a return. Change asks what's wrong, then uses `record_entry`.
- Saved as a purchase with `source: "receipt"`. It counts in money out and profit, and doesn't change the tax estimate, which is based on sales.

**Decisions**

- **Rule 1 holds.** Reading a printed total isn't calculating. The tool description and prompt say to copy it and never add up lines, and with no readable total there is no card. The thumb-over-total test confirms the model declines even when the lines above are clear.
- **Rule 3 holds.** The file is sent once, for that request. It isn't written to localStorage, not sent again with later messages, and not logged; server logs still hold only counts. The picture in the chat bubble is held in memory for that visit, and a reload removes it. A failed send after a reload asks the trader to choose the file again.
- **The picture does leave the phone.** It goes to Anthropic to be read, which the sheet says plainly before the trader picks a photo. For a pilot this belongs with the question of AI processing outside Lesotho (section 13).
- **The Lekuka check is simulated and labelled.** RSL says teams get no access to live systems, so `lib/lekuka.ts` holds seven made-up invoices. It never contacts RSL's real portal. A real connection needs an agreement with RSL and would be a pilot dependency.
- **The check takes only invoice details,** never who the trader is. This keeps the promise that records stay on the phone, and it must stay that way in a pilot.
- **A failed check is never an accusation.** It's usually a misread picture, so the wording stays neutral and the trader can still save.
- **Duplicates.** The same invoice number and device can only be saved once. Without an invoice number, the same date and total from another receipt shows a warning and the trader decides, because a second identical purchase is possible.
- **A large amount needs no second question,** since the trader sees it on the card before tapping Save.
- **Text on a receipt is data, never an instruction.** Tested with a receipt carrying instructions to the assistant.
- **Sample receipts** are drawn by `scripts/make_sample_receipts.py`, with made-up businesses all named "Sample ...", marked "SAMPLE - NOT A REAL INVOICE", with no RSL logo. The layout follows the receipt in RSL's session. The square code on them doesn't scan: Khoebo reads the printed code instead, so no QR library is needed and it also works on a photo of a printed code. Scanning real QR codes is a pilot option.

**Found by the eval and fixed:** on a creased receipt the model guessed a date hidden by a crease, wrong in 5 of 5 runs, while the total stayed right. The prompt now says to leave out any figure with a hidden or smudged digit. After the fix those runs show the card with "The date wasn't clear".

Each network address gets 20 failed log-ins and 10 sign-ups per 15 minutes, counted by keyed hashes of the address that are deleted after a day. A wrong username and a wrong password get the same message, and an unknown username still runs a hash, so the form can't be used to find out who has an account.
